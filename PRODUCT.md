# Product

MeetTape is a Windows desktop application on Avalonia 12 and .NET 10 for recording a microphone (**Me**) and all playback on the selected output device (**Them**) as separate, synchronized MP3 tracks. Recordings and documents stay in the configured meeting folder. Transcription sends audio to a user-configured Chat Completions API; Summary sends the completed transcript.

## Recording and desktop lifecycle

Settings → Recording offers Windows Default (unchanged capture, default for existing users) or Windows Communications for microphone `Me` only. Communications requests OS-managed effects when available but may cause Windows playback ducking; this must be checked for both quiet `Me` speech and unaffected `Them` playback voices. `Them` loopback has no new signal processing, and FFmpeg noise reduction is not enabled. Unsupported Communications requests fail with an actionable message rather than silently falling back. The mode is captured for each new session, while stored recordings and their checkpoints remain unchanged.

The tray and window icons show a red dot in the upper-right corner only while capture is active. Windows taskbar buttons also show a red recording overlay, positioned by Windows, including pinned/grouped buttons. Windows small-icon taskbars do not support overlays. Stop or capture failure restores the original icon; audio preparation/transcription does not show the recording indicator. The permanent EXE/shortcut icon stays unchanged.

The configurable recording hotkey defaults to Ctrl+Shift+F9 and uses the same Start/Stop path while MeetTape runs, including when hidden or another app has focus. Settings → Recording saves and immediately applies a replacement; the window/tray show the active combination. Invalid/occupied replacements or failed configuration writes retain the previous binding, and discarding edits does not apply them. Busy operations, updates, Exit and unfinished naming block conflicting starts. A startup shortcut conflict is diagnosed while buttons/tray remain usable. Windows notifications report successful Start, finalized Stop or interruption without focusing the window or including meeting contents. Suppressed/failed notifications do not affect recording or saved work; window/tray status remains authoritative. The shortcut is released on Exit.

An opt-in Settings → Recording toggle (off by default) offers recording when another process begins using any active Windows microphone capture endpoint. Detection is advisory only: it does not identify a meeting, browser tab or speech, and cannot guarantee every application/driver is visible. It takes an initial baseline to avoid notifying for existing usage, requires successive positive samples, excludes MeetTape's own process, coalesces multiple sessions per app and avoids repeated offers during one continuous activity (with a short app-level cooldown). The Windows toast requires an explicit Start recording click through the existing start-only guard; it never stops capture, starts automatically or bypasses naming/update/exit. Settings Save takes effect immediately; hidden/tray operation continues and Exit disables the observer. No audio content is read by the observer, and failure/suppressed notifications cannot affect recording.

Settings → Reminders has local manually configured one-time reminders (date/time) and recurring reminders (time with any 1–7 selected weekdays). Each may have an optional meeting name and can be edited, enabled/disabled or deleted. The existing Settings Save/Close rules apply, including unsaved edits. One minute before the meeting, a Windows notification offers Start recording or Remind in 5 min, plus standard dismissal. Start uses guarded start-only behavior and never stops existing capture. During recording, no reminder appears. Snooze delays only the current alert; dismissal skips it without canceling future repeats. Occurrence delivery progress survives restart to avoid duplicates, and reminders run while the window is hidden in the tray. An optional installed-build Run with Windows setting launches straight to the tray; explicit Exit stops reminders.

`MeetTape.exe` opens one window and a system tray icon, without a console. The window and tray share Start/Stop. The light main window has an artwork/version/Settings header, a fixed capture card with timer, Me/Them levels and actionable capture errors, followed by searchable Title/Date/Duration/Status rows. Name / Trim remains inside the capture card after Stop. The light theme is retained when Windows is dark; compact widths use vertical scrolling and ellipsis for long titles. Closing the window hides it and does not stop recording. Open from the tray or launch MeetTape again to restore it; a repeated ordinary launch does not create another recorder, job runner or tray icon. Explicit Exit finalizes both MP3s and cancels/joins preparation and processing before the process exits; a new ordinary launch then starts normally. A second Start is rejected.

Start cancels and joins local preparation/API jobs before opening capture; an unconfirmed join blocks capture. No conflicting processing runs during recording. Compact Me/Them bars show independent PCM signal activity during capture, fade without new packets and reset on Stop/new Start; a natural pause is not an error. Stop finalizes audio on a worker, then awaits an optional meeting title and trim decision. Jobs remain deferred while the just-stopped recording awaits its title; Continue saves the title (empty is unnamed), offers trimming when enabled and lets eligible processing resume. Start next recording saves the optional title and starts another capture in one action; unfinished trim can be reopened through Name / Trim afterward. A failed start retains the previous meeting and leaves recording available to retry. Capture failures retain surviving audio and restart deferred jobs for eligible earlier meetings.

The tray keeps recording status first and shows a separate short processing state: queued work, chunk progress, retry, completion or a pause requiring attention. Processing is explicitly deferred during capture. The tooltip contains status/counts without meeting contents or long diagnostics. The session list shows dates, title, capture/job states, chunk counts, retry time and diagnostics. Search matches title (including Unnamed meeting) and the displayed date without reading documents. Refresh updates individual rows while retaining unchanged items and selection; filtered or removed selections disable their actions. Select a meeting with one click; double-click opens its folder. Right-click a row or use its three-dot button for the same row menu: folders/documents, Copy, Name / Trim, Resume, Summary, Cancel, Delete and live copyable Details with full stage/chunk progress and diagnostics. Existing action eligibility and deletion confirmation apply; no action panel sits below the table. Copy… offers Copy transcript/Copy summary only for existing documents; the explicit action reads the original Markdown and sends it to the clipboard without editing files, starting jobs or caching document contents. Resume processing is available for recoverable paused or canceled processing, after capture and trim are complete; automatic retries need no manual resume. Request Summary requires a complete published transcription regardless of Automatic Summary; a pending, running or paused request is not offered again. A completed Summary can be restored from its saved checkpoint if summary.md is missing, without another API request. Automatic Summary queues one Summary for new recordings; enabling it does not request summaries for historical completed meetings. UI/controller state and processing notifications are typed; technical WASAPI anomalies do not produce user-facing warnings. Capture timing corrections persist in session metadata. Saved settings apply without restarting. Capture devices, output folder, FFmpeg, stages and chunk duration apply to the next recording; an active recording retains its streams and session contract. Running jobs keep saved processing parameters, and explicit Resume uses current API settings without resending successful chunks. Earlier meeting roots remain visible and scheduled in the current app lifetime after changing the output folder. User arguments show a GUI error without loading settings, recording or processing.

The Meetings context menu offers Delete recording for a selected finalized meeting whose processing is completed or explicitly canceled. Confirmation shows its title/date and warns that the entire folder and all audio, metadata, checkpoints and documents move to Windows Recycle Bin. Cancel retains the meeting. Capture, unfinished naming, active preparation/jobs, invalid or changed identity/path and linked folders/files refuse deletion. Only a direct child of a known meetings root is accepted; configuration and unrelated folders are protected. An unavailable Recycle Bin reports failure without a permanent-delete fallback. Success removes the meeting and selection; other meetings remain available.

Failed or Interrupted recordings can also be explicitly deleted after capture and related operations finish. Their partial files use the same confirmation, folder ownership checks and Recycle Bin path; running jobs/stages still block deletion.

Failed or Interrupted recordings offer an explicit Recover recording action in the meeting context menu. Recovery verifies the selected session identity, finalized MP3 frame/byte counts, full FFmpeg decoding, synchronized original track durations and saved time boundaries before changing metadata to Recorded. Interrupted sessions without a saved duration can derive it from verified finalized audio; failed sessions require a saved duration. Recovery never changes original audio or checkpoints. Failed validation leaves the session unchanged and displays the reason. Recovered sessions with unfinished trimming require Name / Trim; others can use Resume processing to restart incomplete stages deliberately.

## Updates

Settings / About shows versions and separate Check for updates and Update controls. Check only queries availability and leaves recording usable; it never downloads, applies or joins jobs. Update requires an available installed update, safe idle state and saved/discarded settings, then uses the existing confirmation/download/restart sequence. Settings editing/closing is blocked during that sequence; progress remains visible. Update and Exit are absent from the main header; Exit remains in the tray.

Significant failures show a readable cause and an available recovery action. Technical exception context and workflow transitions are saved in `%LOCALAPPDATA%\MeetTape\Logs`, retained after restart and bounded to five 1 MiB files. Open logs folder in Settings opens the current log directory in Windows Explorer, creating it if absent and showing safe access/shell errors. It preserves settings, recordings and log files and works independently of Save; no in-app log viewer is added. API diagnostics include stage/session/chunk/attempt, server authority, requested/returned model, duration, HTTP status, response size, available correlation IDs, choices/content shape, finish/block reason, token counts and retry/pause decisions. Structured HTTP errors distinguish unknown models, unsupported audio input, provider blocks and limits using safe reason categories. Arbitrary error messages and unknown error codes are redacted; metadata strings are bounded and restricted. API keys, prompts, transcripts and audio payloads are not logged; credential values and URL credentials are redacted. Logging is nonblocking for capture and best-effort when storage is unavailable.

GUI startup displays the installed version and checks the public Velopack GitHub feed with a bounded two-second wait. Failures do not block capture; source/portable builds skip the check. Update requires idle capture and no unfinished naming/current operation. It shows current/available versions and asks for explicit consent before downloading. Decline/close leaves the UI usable; even a previously downloaded package never auto-applies on startup. After download, capture is checked again and local work is joined before applying/restarting. Failed joins block apply. Use Exit in other MeetTape windows/trays first.

## Configuration

Velopack Setup installs MeetTape and bundled FFmpeg 9.0 for the current user without UAC, creates a Start menu shortcut and registers the Windows uninstaller. The existing cassette artwork supplies one multi-size Windows icon for the EXE, window, tray, shortcuts and installer/updater metadata. Updates/uninstall retain user config, prompts, recordings, checkpoints and API key environment variables. Settings selects concrete or Windows-default devices, meetings folder, FFmpeg, trim/transcription/Summary stages, chunkSeconds, endpoints/models, prompt paths and credential variable names. Candidate JSON passes the existing loader/prompt validation before atomic replacement, under the existing configuration mutex. Concurrent file edits are detected; unchanged files and user prompts are retained. Settings groups fields into Recording, Processing and API & prompts tabs. Transcription/Summary each have a separate file path and multiline content editor with standard selection/copy/paste. Load file resolves paths against config.json and retains unsaved text instead of redirecting it to another path. Save validates enabled instructions and compares all edited sources before any replacement, then flushes each edited UTF-8 Markdown file to an atomic replacement. An I/O failure retains remaining edits and reports that earlier files may have been saved; retry uses their new baseline. Closing with any unsaved field or prompt asks Keep editing / Discard. Ordinary saves never restore templates.

The default file is `%APPDATA%\MeetTape\config.json`, still directly editable. On first use editable configuration and default prompts are created without overwriting existing files. Installed and source builds use this same user settings path. Prompt and meetings paths must remain outside the installation directory. Relative meetings/prompt paths resolve from the configuration directory. FFmpeg selection prefers an adjacent ffmpeg.exe when configured by its default name.

Existing API keys are never loaded into controls. New keys use masked fields and are saved only to the Windows User environment and the current process, never JSON, prompts, logs or session metadata. Empty fields retain existing credentials. These variables are user registry storage, not an encrypted secrets vault. New keys are available to MeetTape immediately; other running terminals may need reopening to inherit changed variables. Keys are optional for recording; missing or invalid credentials pause API processing without exposing their values.

API requests use the named Process environment key, falling back to the Windows User environment when the Process value is absent. Missing or empty enabled prompt files do not disable recording; they pause the affected processing stage with a safe diagnostic. Fix the prompt file or key, save changed settings, then use Resume; completed chunks are retained.

All shipped UI messages and prompt instructions are in English. The default transcription prompt still targets Russian (`ru`), and the default Summary requests Russian output; the instruction language does not change the speech/result language. New transcript preambles are English, while utterances keep their source text. First-use defaults are user-editable; existing custom prompts and published documents are never overwritten by template updates. `stages.summary` requires `stages.transcribe`; chunkSeconds accepts 1–340 seconds. Restart also restores eligible saved jobs and presents unfinished trim selection through Name / Trim; no new Summary request is inferred from startup.

## Trimming and transcription

Failed or canceled trim/chunk attempts discard only their unselected derivative directory after FFmpeg has stopped. Original recordings, selected successful derivatives and checkpoints remain. Failed selection persistence also discards the unselected attempt. If FFmpeg cannot be confirmed stopped, metadata cannot safely identify the selected set, or cleanup storage/links are unsafe, files remain and technical diagnostics are logged.

Edge-silence detection considers activity in both tracks. Choose Accept, Skip or Apply interval in the window; manual times accept seconds, `MM:SS` or `HH:MM:SS` and require `0 <= start < end <= duration`. Both tracks use one shared interval; interior silence remains. No detected activity keeps the full recording. Name / Trim reopens unfinished preparation. Originals remain unchanged; selected derivatives are saved only after successful preparation.

After a saved trim choice, or with trimming disabled, enabled transcription runs serially in the background and resumes eligible unfinished jobs at GUI startup. Every time interval produces two independently uploaded mono MP3 chunks, Me and Them, retaining shared timestamps and boundary context. Each has its own durable checkpoint, so there are twice as many API requests as in the former stereo pipeline. Existing prepared stereo chunks and their checkpoints remain usable on Resume. Successful results are saved before progress advances; only a complete set produces `transcription.md`.

Cancel processing is available immediately after Stop and for a selected meeting with unfinished work. It joins only that meeting's preparation/API work and saves Canceled before allowing further processing; other meetings and new captures remain available. Canceled meetings never restart automatically. Resume processing explicitly continues prepared work; unfinished Name / Trim reopens preparation. Audio, checkpoints and existing documents remain intact. A request already sent may still be billed; a successful result received before cancellation is saved when possible. Failed cancellation or metadata saving reports an error instead of claiming a durable cancellation.

The transcript has approximate timestamps relative to the original recording. Unambiguously joined local timestamp markers in mono replies are separated for parsing while preserving the model's words, values and original checkpoint text. Mono timestamp order is checked before chronological assembly; ambiguous fragments and partial/truncated speech remain invalid. New mono responses are labeled Me/Them by their recorded source and combined in chronological order, preserving simultaneous speech. For new mono chunks the parser accepts Me/Them/Unknown labels or a timestamped line with no label, inferring the source locally; ordinary spoken text with a colon is not treated as a speaker name, but unsupported explicit labels are rejected. Historical stereo checkpoints keep their legacy parsing and model-estimated source labels. Settings / Processing lets the user provide a Me display name (for example, `Артём О`), applied only in Markdown after transcription. Repeated same-source boundary context is reconciled conservatively. Microphone audio can contain playback echo and duplicate speech across tracks; no AEC or cross-track deduplication is performed.

An exact `[NO_SPEECH]` response, or a mono silence-only response with an otherwise valid timestamp/recording-source wrapper, adds no utterances. This is a model claim, not independent verification that the audio is silent. Each chunk's timed text is checked and safely normalized before the next upload. Invalid timed replies that cannot be safely normalized are retained and retried automatically once against the original audio after one second; if still invalid, processing pauses. Successful checkpoints retain the original reply; the rejected original of each invalid attempt remains in `chunks/*.rejected-*.json` for diagnosis. On Resume, an earlier rejected reply that now validates against the same audio, model and prompt is reused without another API request; otherwise only the rejected chunk is retried, retaining earlier valid checkpoints. Empty, malformed or truncated responses also pause processing. Each audio upload is limited to 8 MiB, each API response to 2 MiB, and each request to five minutes.

## Summary

Settings / Processing / Automatic Summary queues `summary.md` for new recordings after the complete transcript is published. With automatic mode off, Request Summary remains available for a completed transcript. Both modes use independent API settings and an editable prompt; persisted requests survive restart/Resume without repeating saved successes. It never replaces the transcript or summarizes partial results. Combined prompt/transcript UTF-8 input is limited to 2 MiB; oversized input pauses without truncation. A provider may enforce a smaller context limit.

For completed transcription/assembly, Summary uses the published Markdown verified against its saved SHA-256, without reading intermediate MP3s/checkpoints or assembling again. Missing intermediate audio does not block Summary. A missing or changed published transcript pauses the Summary stage without re-creating the document or sending text, including restoration from a saved Summary checkpoint.

Successful Summary results are checkpointed before publication. Repeated requests retain existing output; missing output can be restored from its checkpoint without another API request.

## Files and saved progress

Each recording has a unique folder and stable session ID under `meetingsRoot`:

New captures may use a temporary internal name. Stop or Exit gives finalized audio an `Unnamed meeting_dd.MM.yyyy HH-mm HHhMMm` folder; saving a title replaces only the name prefix. Start time is local, duration uses saved audio and whole hours/minutes. Windows-invalid filename characters are replaced while ordinary Unicode/spaces remain. Folder names contain no UUID; occupied names receive the next available ` (2)`, ` (3)`, ... suffix. Existing folders/files are preserved; Stop and ordinary Continue / Start next recording choose a unique folder automatically. On Exit, a naming failure retains the finalized source folder and reports an error without blocking shutdown. Existing sessions are not renamed in bulk, and their UUID/file schema stays unchanged.

- `me.mp3`, `them.mp3`: preserved source recordings.
- `session.json`: identity, title, capture parameters, selected interval, stages, progress and diagnostics.
- `processed/`: selected trim derivatives and stereo chunks when needed.
- `chunks/`: successful transcription checkpoints.
- `transcription.md`: complete transcript; `summary.json` and `summary.md`: optional Summary checkpoint and document.

Only the current session/checkpoint model is supported. Legacy recovery manifests and compatibility across previous versions are not provided; unsupported metadata is diagnosed while its original files remain untouched.

Exiting MeetTape retains saved progress. Restart validates and reuses completed chunks without re-uploading them. Corrupt or mismatched checkpoints pause the job. Differing existing transcript/Summary documents are preserved and diagnosed.

Timeouts, HTTP 408/429/5xx and temporary connection faults retry indefinitely with exponential backoff capped at five minutes, including capped Retry-After. For a transcription chunk, HTTP 200 with an empty choices array and no explicit provider block retries within a three-attempt budget, with one- and two-second backoff for consecutive empty responses. The saved attempt count/deadline survives restart; earlier successful chunks are not resent. Exhaustion pauses with a clear reason and requires explicit Resume. Provider blocks, other HTTP errors, malformed API responses and configuration/filesystem faults pause the affected job without a new format retry. A timed-text format failure has a separate one-retry budget persisted per chunk, independent of the HTTP/empty-choices retry count. Fix the cause, save changed settings, then use Resume. If saving a pause fails, the GUI reports it and blocks that session in the current process.

Device, encoder or storage failures stop both sources and retain surviving audio; already accepted PCM is flushed to MP3 when possible before a forced encoder shutdown. After an asynchronous capture failure, deferred processing automatically resumes for other eligible recordings. Failed recordings retain surviving originals for manual verification and do not enter automatic processing. WASAPI timestamp errors, clock resets and overlapping packet positions never stop capture on their own: the recorder places late packets after committed audio and uses arrival time when QPC metadata is invalid. This prioritizes retaining speech over exact alignment. Technical WASAPI timing anomalies do not show banners in the capture card or tray. The compact capture panel shows status, duration and actionable capture errors with available recovery hints; background job issues appear separately and the contextual Details of each meeting remains available. Per-track correction counts, invalid timestamp counts, largest shifts, discontinuity counts and the latest timing details remain in `session.json`. Both MP3s are finalized at a common length, including recovered speech that extends beyond the wall-clock stop time; `session.json.durationSeconds` reflects the saved audio length and `endedAtUtc` remains the actual stop time. Abandoned captures are reported as interrupted with processing paused; they are not automatically declared complete. Capture streams audio without keeping the whole recording in memory. Trimming and chunk preparation accept recordings up to three hours; capture does not stop automatically at that boundary. Full-duration hardware capture remains unverified.
